# Sculith 고성능 게임 서버 엔진 전면 최적화 프로젝트

## 0. 프로젝트 목표

GitHub Repository: https://github.com/SKYRPG8957/Sculith

Sculith는 Rust 기반의 Minecraft Java·Bedrock 통합 서버 엔진이다.

이번 작업의 목표는 단순한 코드 경량화가 아니라, 실제 상용 게임 엔진 및 대규모 멀티플레이 서버에서 활용하는 최적화 기술을 Sculith의 아키텍처에 도입하는 것이다.

**최종 목표**

- 멀티코어 CPU 활용 극대화
- 게임 시뮬레이션 지연 최소화
- 대량 엔티티·블록·청크 처리 효율 개선
- 메모리 사용량과 메모리 할당 비용 절감
- 네트워크 대역폭 및 패킷 처리 비용 감소
- 원거리 렌더링과 시뮬레이션 최적화
- 대규모 동시접속을 위한 확장 가능한 서버 구조 확보
- Java·Bedrock 크로스플레이 호환성 유지
- 장기적인 성능 회귀를 자동으로 탐지하는 시스템 구축

Rust의 특성을 적극 활용하되, 언어 자체의 성능에만 의존하지 말고 알고리즘·데이터 배치·작업 스케줄링·캐싱·메모리 관리까지 최적화한다.

**중요: 기획서만 작성하지 말 것. 실제 저장소의 코드를 분석하고, 안전하게 구현 가능한 항목은 직접 수정·테스트·벤치마크할 것.**

# 2. Data-Oriented Design 및 ECS

상용 게임 엔진에서 사용하는 데이터 중심 설계를 도입한다.

## 구현 목표

- Array of Structures(AoS)와 Structure of Arrays(SoA) 비교
- 엔티티 구성요소별 연속 메모리 배치
- 캐시 친화적인 엔티티 순회
- 불필요한 포인터 역참조 감소
- 데이터 복사 및 임시 객체 생성 최소화
- Generational Entity ID 도입 검토
- 엔티티 종류별 저장 구조 최적화
- SIMD 적용이 가능한 데이터 배치

향후 몬스터, 플레이어, 투사체, 아이템 엔티티 등의 대량 처리를 고려한다.

기존 Rust 코드와 호환되는 ECS를 선택적으로 활용한다.

Bevy ECS, hecs 등 기존 라이브러리의 장단점을 검토하되, 단순히 ECS 도입 자체를 목적으로 엔진 전체를 재작성하지 않는다.

실제 벤치마크에서 이점이 입증된 데이터 구조를 선택한다.

# 3. Regionized Multithreading

Folia와 같은 Region 기반 멀티스레드 시뮬레이션 구조를 참고한다.

## 핵심 설계

- 지역별 단일 소유권
- 지역 간 독립적인 게임 상태 처리
- 다수 Region의 병렬 시뮬레이션
- 동적 Region 분할 및 병합
- Region별 작업 큐
- Worker Thread Pool
- 지역별 부하 측정 및 스케줄링
- 서로 다른 Region 사이의 안전한 메시지 전달

Region과 CPU 코어를 1:1로 고정하지 않는다.

작업 스케줄러가 CPU 사용량, Region 부하, 작업 대기시간을 고려해 실행을 분배하도록 설계한다.

### 안전성 요구사항

- 동일 Region의 상태를 여러 스레드가 동시에 변경하지 않도록 한다.
- 엔티티의 Region 간 이동 시 소유권을 안전하게 이전한다.
- 경계에 걸친 블록 업데이트와 충돌 판정을 보장한다.
- 교착 상태와 데이터 경합을 방지한다.
- 시뮬레이션 순서와 결정성이 필요한 게임 규칙을 유지한다.
- 글로벌 상태 접근을 최소화한다.

현재 단일 월드 소유자 구조에서 점진적으로 이행할 수 있도록 설계한다.

**단순히 Tokio 태스크를 여러 개 생성하는 것을 RMT 구현으로 간주하지 않는다. 실제 게임 상태 계산이 병렬 수행되는지 검증한다.**

# 4. Work-Stealing Job System

게임 엔진용 작업 스케줄러를 설계한다.

작업을 다음과 같이 분류한다.

**Critical Jobs**
- 게임 시뮬레이션
- 플레이어 입력 처리
- 필수 블록 및 엔티티 업데이트

**High Priority Jobs**
- 플레이어 주변 청크 로딩
- 필수 충돌 데이터 준비
- 네트워크 전송 준비

**Background Jobs**
- 청크 사전 생성
- LOD 생성
- 데이터 압축
- 저장 및 백업
- 비필수 캐시 생성

구현 요구사항:

- 제한된 작업자 스레드 풀
- Work-Stealing
- 우선순위 스케줄링
- 작업 취소
- 큐 길이 제한
- CPU 처리 예산
- 과부하 방지
- 작업 의존성 관리
- 지연시간 측정

기존 Tokio는 비동기 I/O에 활용하고, CPU 집약적 작업은 별도 실행기 사용을 검토한다.

게임 지연이 증가하면 낮은 우선순위 작업의 실행량을 자동으로 줄인다.

CPU 사용률 100% 자체를 목표로 삼지 않는다.

**게임 틱의 안정성과 사용자 응답성을 최우선으로 한다.**

# 5. Event-Driven Simulation

불필요한 반복 계산을 최소화한다.

## 구현 대상

- 블록 상태 변경
- 레드스톤
- 유체 업데이트
- 예약 틱
- 엔티티 상태 변화
- 주변 객체 활성화
- 게임 이벤트 전파

최적화 방식:

- Dirty Flag
- 이벤트 중복 제거
- 이벤트 병합
- 의존성 그래프
- 변경 기반 업데이트
- 이벤트 큐 분할
- 비활성 상태 계산 생략
- 캐시된 상태 재사용

불필요하게 매 틱 전체 데이터를 탐색하는 방식을 줄인다.

단, 바닐라 호환성이 필요한 랜덤 틱·예약 틱·레드스톤 순서는 임의로 변경하지 않는다.

최적화 전후 게임 결과의 동등성을 검증한다.

# 6. Simulation LOD

렌더링 LOD뿐 아니라 서버 시뮬레이션 자체에도 LOD를 도입한다.

## 시뮬레이션 단계

**Level 0 — Full Simulation**

플레이어와 직접 상호작용하는 지역에서 정상 시뮬레이션을 수행한다.

**Level 1 — Reduced Simulation**

플레이어와 가까우나 직접 상호작용하지 않는 엔티티의 비필수 계산을 줄인다.

**Level 2 — Background Simulation**

먼 지역의 경로 탐색 및 비필수 AI 계산 빈도를 낮춘다.

**Level 3 — Dormant State**

게임 규칙상 비활성화가 허용되는 객체를 이벤트 기반으로 관리한다.

### 필수 조건

- 게임 결과의 정확성 유지
- 필수 틱 및 상태 변화 보존
- 활성화 전환 시 상태 동기화
- 플레이어 접근 시 빠른 복구
- 게임 규칙상 안전한 대상만 최적화

바닐라 동작을 깨뜨리는 무분별한 틱 생략은 금지한다.

두 에디션의 패킷 규격과 클라이언트 동작을 반드시 준수한다.

# 8. 네트워크 및 패킷 처리 최적화

다음 기법을 검토하고 실제 병목이 확인된 부분에 적용한다.

- Zero-Copy에 가까운 데이터 흐름
- 재사용 가능한 패킷 버퍼
- Scatter/Gather I/O
- 변경 기반 인코딩
- 인코딩 캐싱
- 공유 가능한 불변 패킷 데이터
- 불필요한 직렬화 제거
- 불필요한 메모리 복사 감소
- 전송 작업 배치
- 압축 수준의 동적 선택
- 연결별 Backpressure
- 네트워크 큐 상한
- 대량 접속 시 공정한 작업 분배

Java TCP와 Bedrock 전송 프로토콜의 특성을 각각 고려한다.

프로토콜에 정의되지 않은 임의 압축 방식을 클라이언트에 전송하지 않는다.

# 9. Packet-Only LOD

Sculith 공식 설계에 존재하는 Packet-only LOD를 발전시킨다.

## 필수 구성

- Shared LOD Tile Cache
- Multi-Level LOD
- 지형 높이 기반 메시 생성
- 표면 분류
- 거리 기반 타일 선택
- Dirty Tile Tracking
- 증분 업데이트
- 비동기 LOD 생성
- LOD 캐시 저장
- 캐시 무효화
- 플레이어별 렌더링 예산
- 클라이언트 성능별 품질 설정

LOD 표현을 실제 게임 엔티티 시뮬레이션과 분리한다.

Bedrock의 모델·Actor 표현 한계를 검증하고 지원 가능한 지형 표현만 구현한다.

Java 클라이언트의 경우 별도 LOD 지원 경로를 연구하되, Bedrock 구현과 무리하게 동일한 표현 방식을 강제하지 않는다.

게임 틱이 지연되면 LOD 생성 작업을 자동으로 제한한다.

# 10. 메모리 최적화

Rust의 메모리 관리 특성을 활용한다.

검토 대상:

- Object Pool
- Arena Allocation
- Slab Allocation
- Small Vector Optimization
- Copy-on-Write
- Immutable Snapshot
- 문자열 및 블록 ID Interning
- 캐시 친화적 자료구조
- 불필요한 Clone 제거
- 메모리 레이아웃 최적화
- 메모리 단편화 감소
- 장기 유지되는 캐시의 크기 제한

모든 객체에 풀링을 적용하지 않는다.

메모리 할당량, 할당 횟수, 메모리 사용량, 처리시간을 함께 측정한 뒤 선택한다.

기존 워크스페이스의 `unsafe_code = "forbid"` 정책을 유지한다.

불가피한 저수준 최적화는 안전한 대안을 먼저 검토하고, 별도 승인이 필요한 작업으로 보고한다.

# 12. 플러그인 시스템 최적화

현재 Sculith 플러그인 시스템의 실제 구조를 분석한다.

최적화 대상:

- 이벤트 직렬화
- 이벤트 전달 지연
- JSON-lines IPC 비용
- 플러그인별 처리시간
- 대량 플러그인 호출
- 이벤트 구독 필터링
- 이벤트 배치
- 플러그인 격리
- 불필요한 데이터 복사

IPC를 무조건 교체하지 않는다.

기존 SDK와 프로토콜 버전 호환성을 유지하고, 벤치마크에서 이점이 입증되면 바이너리 IPC 또는 공유 메모리 기반 통신을 검토한다.

플러그인 실행 지연과 실제 CPU 사용량을 분리하여 측정한다.

향후 Perry 기반 TypeScript 네이티브 플러그인 및 WASI Component 플러그인을 지원할 수 있도록 엔진 API의 결합도를 낮춘다.

수집한 데이터는 향후 Sculith Manager가 조회할 수 있는 안정적인 인터페이스로 제공한다.

Manager를 설치하지 않아도 서버의 성능에 불이익이 없도록 한다.

# 14. Adaptive Performance Controller

게임 부하에 따라 서버가 백그라운드 작업량을 자동 조정하는 시스템을 설계한다.

입력 지표:

- CPU 사용량
- 처리 지연
- 활성 Region 수
- 작업 큐 길이
- 메모리 사용량
- 패킷 전송 지연
- 디스크 I/O 지연

조절 대상:

- LOD 생성 병렬도
- 청크 사전 생성량
- 압축 작업 병렬도
- 백그라운드 저장 작업량
- 캐시 정리 빈도
- 비필수 작업 동시 실행량

필수 게임 로직의 실행 빈도나 정확성을 임의로 낮추지 않는다.

부하가 증가하면 저우선순위 작업부터 제한한다.

작업량이 계속 변동하는 현상을 막기 위해 히스테리시스와 조절 주기 제한을 적용한다.

# 16. 개발 원칙

다음 원칙을 반드시 준수한다.

1. 기존 기능과 Java·Bedrock 호환성을 보존한다.
2. 최적화를 위해 게임 동작을 임의로 변경하지 않는다.
3. 이미 효율적인 코드를 불필요하게 재작성하지 않는다.
4. 실제 병목이 확인된 부분을 우선 개선한다.
5. 새로운 의존성은 이점과 유지보수 비용을 검토한다.
6. 안전한 Rust 코드를 기본으로 한다.
7. 데이터 경합·교착·메모리 누수를 방지한다.
8. 모든 병렬 작업에는 종료·취소·오류 처리 경로를 마련한다.
9. 기능을 추가할수록 성능이 자동으로 퇴보하지 않도록 회귀 테스트를 작성한다.
10. 각 최적화가 실제로 효과가 있는지 수치로 검증한다.

기존 엔진의 보안·인증·패킷 검증·플러그인 격리 정책은 약화하지 않는다.

# 17. 실제 구현 순서

작업을 분석으로 끝내지 말고 다음 단계에 따라 진행한다.

**Phase 1 — Baseline & Profiling**

현재 성능 측정, 벤치마크 구축, 프로파일러 계측을 먼저 수행한다.

**Phase 2 — Low-Risk Optimization**

데이터 복사, 불필요한 할당, 이벤트 중복, 패킷 인코딩 및 캐시 최적화를 진행한다.

**Phase 3 — World & Simulation Architecture**

Data-Oriented Design, ECS, Spatial Partitioning, Event-Driven 구조를 도입한다.

**Phase 4 — Parallel Execution**

Regionized Multithreading과 Work-Stealing Job System을 구현한다.

**Phase 5 — Advanced Optimization**

Simulation LOD, Packet-only LOD, Adaptive Performance Controller, 비동기 청크·저장 시스템을 확장한다.

**Phase 6 — Validation & Stabilization**

고부하 테스트, 메모리 안정성, 회귀 테스트, Java·Bedrock 실클라이언트 호환성을 검증한다.

각 Phase는 구현 가능한 단위로 나누고, 독립적으로 테스트할 수 있도록 한다.

한 번의 작업에서 전체 구현이 불가능하다면 안전하게 완성하고 검증한 단계까지만 반영한다.

미완성 기능을 완성됐다고 보고하지 않는다.
