# 개발 단계와 완료 기준

최종 목표는 베드락을 기준으로 정의한 월드·콘텐츠·규칙에 두 에디션이 함께 참여하는 서버입니다.
아래 순서로 의존성을 쌓고, 단계별로 실제 클라이언트 검증을 추가합니다.

## 0. 개발 기반 — 현재

- [x] Rust 워크스페이스, 버전 고정, 반복 가능한 빌드와 CI 정의
- [x] 두 에디션의 서버 목록 응답과 공통 상태
- [x] Rust 플러그인 실행·버전 검증·생명주기 훅·공통 MOTD 액션
- [x] 명시적 베드락 PNG → 자바 텍스처 대응 변환
- [x] 실제 TCP/UDP와 Rust 플러그인을 사용하는 로컬 스모크 테스트

서버 목록 응답은 월드 접속이나 크로스플레이 완료 기준이 아닙니다.

## 1. 최신 베드락 클라이언트의 첫 월드 입장

- [x] Rust 라이브러리를 사용한 RakNet 세션과 실제 UDP 헤드리스 통합 테스트
- [x] 네트워크 설정·배치·압축·서명 검증·암호화와 세션 수명주기
- [ ] 공식 온라인 인증 서비스 연동 검증과 실제 Minecraft 클라이언트 입장
- [ ] 리소스팩 협상, 시작/스폰 패킷과 최신 런타임 레지스트리
- [x] 읽기 전용 평지 청크 인코딩·전송·스폰 확인과 연결 종료(헤드리스 검증)
- [ ] 권위 있는 이동·기본 블록 상호작용
- [ ] NetherNet 연결·인증·팩 협상의 독립 구현·검증

완료 기준: 실제 최신 정식 Bedrock 클라이언트가 인증 후 월드에 입장하고,
청크를 확인·이동한 뒤 재접속할 수 있습니다. 잘못된 인증과 손상된 패킷은 거부해야 합니다.

## 2. 공유할 베드락 기준 월드와 게임 API

- [x] 단일 지역 소유권, 내부 블록 ID, 팔레트 section, immutable snapshot, 원자적인 revision commit
- [ ] 예약 틱·차원·엔티티와 클라이언트 입력의 권위 있는 commit 연결
- [ ] 블록 설치·파괴, 인벤토리·아이템, 권한과 서버 측 판정
- [x] 네트워크 ID와 독립된 내부 식별자, 버전·체크섬이 있는 region snapshot 저장·복구 API
- [ ] 서버 자동 저장·재시작 복구 연결
- [ ] 공통 플레이어·채팅·블록 이벤트와 Rust 플러그인 액션

완료 기준: 서로 다른 두 베드락 클라이언트가 같은 상태를 보고,
재시작 뒤에도 월드가 유지되며, 플러그인이 실제 게임 이벤트를 처리합니다.

## 3. 순정 자바 연결과 양방향 플레이

- [ ] Java 인증 및 로그인·설정·플레이 상태 전이
- [ ] Java와 Bedrock의 블록·아이템·엔티티·차원·텍스트 대응표
- [ ] 같은 코어로 들어오는 입력과 청크·엔티티·인벤토리 출력 변환
- [ ] 에디션을 구분하는 계정 식별과 권한 처리
- [ ] 최신 Java 정식 버전 및 검증된 인접 버전의 독립 어댑터

완료 기준: 순정 Java와 최신 Bedrock 클라이언트가 동시에 같은 월드에서
서로를 보고 이동·채팅·블록 변경을 하며, 동일한 플러그인 규칙이 적용됩니다.

## 4. 콘텐츠 변환과 운영

- [ ] 팩 배포·해시·동의/거부·버전 관리
- [ ] 텍스처 대응표 확장, 지원 가능한 블록·아이템 모델 변환
- [ ] 지원 불가능한 UI·애니메이션·스크립트의 대체 표현과 명확한 진단
- [ ] 동시 접속 부하, 재접속·타임아웃·자원 사용량 검증
- [ ] 최신 릴리스 확인 → 어댑터 갱신 → 회귀·실제 클라이언트 검증 절차

사용자의 전체 요구 범위는 [엔지니어링 지침](engineering-directive.md)에 유지합니다.
WASI Component 플러그인, Regionized Multithreading, 선택적 Fabric Companion,
최신 카메라와 packet-only LOD는 위 기본 접속·권위 월드 경로에 이어 구현할 대상이며 현재 지원 기능이 아닙니다.

완료 기준: 하나의 원본 팩에서 두 클라이언트용 콘텐츠가 재현 가능하게 생성·배포되고,
지원 범위와 차이가 운영자에게 명확히 표시됩니다.
